RAG Evaluation Guide

Effective RAG evaluation splits into two layers — retrieval quality and generation quality — with the minimum viable pair being context recall (did retrieval find what was needed?) plus faithfulness (is the answer grounded in what was retrieved?). Everything else layers diagnostic precision on top of those two. No single catch-all metric exists.

1. Retrieval Layer Metrics

Cheap, deterministic when you have labels, and they diagnose the upstream failure mode — if retrieval misses the evidence, no generator can recover.

  • Recall@k — fraction of all relevant chunks in the corpus that made it into the top-k. The "honest retrieval metric" and the cheapest high-signal thing to track.
  • Precision@k — the relevant fraction within the top-k; catches irrelevant chunks diluting the context window.
  • Context precision — reference-free variant asking whether the best chunks are ranked first, not merely present.
  • Context recall — whether retrieved context contains everything needed to answer. Requires a gold answer. Sometimes called "context sufficiency."
  • MRR and nDCG — ranking-order metrics. MRR asks whether correct docs appear early; nDCG applies graded relevance with position weighting. Use these specifically when tuning a reranker, since both are sensitive to ordering rather than mere set membership.

2. Generation Layer Metrics

  • Faithfulness — every claim in the answer supported by retrieved context. The single most important metric to alert on in production.
  • Groundedness — the per-sentence version of faithfulness. Matters most for citation reliability, because whole-answer faithfulness can pass while an individual sentence is unsupported.
  • Answer relevance — does the response actually address the query, or drift.
  • Answer correctness — factual alignment with a gold answer, including completeness.
  • Hallucination rate — reference-free safety net measuring what share of answers are fabricated.
  • Chunk attribution — what share of the answer came from retrieval versus the model's parametric prior. Underused, and directly relevant to proving a claim traces to a source document.

Classic n-gram overlap metrics (BLEU, ROUGE, METEOR) and BERTScore still appear in generation-level lists, but they measure surface similarity to a reference rather than grounding. Treat them as weak proxies.

4. Reference-Based vs Reference-Free

"Needs reference?" asks whether a metric requires a pre-written ground-truth answer (a gold answer or labelled relevant document set) to be computed at all.

Reference-based metrics compare output against something a human wrote in advance. Reference-free metrics evaluate using only artifacts the system produced at query time — the question, the retrieved chunks, and the generated answer.

For a query like "Which DISARM techniques appeared in the 2024 Moldova campaign?":

  • Faithfulness (no reference) — an LLM judge decomposes the answer into claims and checks each against retrieved chunks. It never needs to know the correct answer, only whether the answer is consistent with the retrieved evidence.
  • Context recall (needs reference) — you must already know that chunks 7, 12, and 31 contain the true answer. Without that labelled set, "recall" has no denominator.

Why it matters practically

This is really a distinction about cost and coverage.

  • Reference-free metrics run on live production traffic, on any query, with no annotation work. This is why faithfulness and hallucination rate are the standard production alerting metrics.
  • Reference-based metrics only run on a fixed evaluation set built by hand. Higher fidelity, but they cost annotation hours and say nothing about queries outside that set.

Recall@k, nDCG, MRR, and answer correctness all sit on the "yes" side because each needs a human decision about what counted as relevant or correct.

The trap in the middle

Reference-free does not mean assumption-free. Faithfulness measures grounding in retrieved context, not truth. If the retriever pulls a wrong-but-confident chunk and the generator faithfully summarizes it, faithfulness scores 1.0 on a wrong answer. Reference-based metrics catch that failure.

For comparing two hybrid BM25-plus-vector configurations this is decisive: reference-free metrics look nearly identical across both configs, because both faithfully summarize whatever they retrieved. Only a labelled gold set gives recall@k and nDCG, where the actual difference between retrievers shows up.

5. Recall@k vs Context Recall

Both measure "did we retrieve the evidence we needed," but they count different things. Recall@k counts documents against a labelled relevance set; context recall counts claims in the gold answer against the text of the retrieved chunks.

Recall@k — document-level set overlap

Classic IR metric. Label which chunks in the corpus are relevant, retrieve the top-k, and compute:

Recall@k=∣relevant chunks in top-k∣∣all relevant chunks in corpus∣ \text{Recall@k} = \frac{|\text{relevant chunks in top-}k|}{|\text{all relevant chunks in corpus}|} Recall@k=∣all relevant chunks in corpus∣∣relevant chunks in top-k∣​

The unit of accounting is the document ID. Deterministic, cheap, reproducible — no LLM in the loop, just set arithmetic. Ground truth is a list like ["doc_7", "doc_12", "doc_31"].

Context recall — claim-level coverage

RAGAS-style metric. Ground truth is a written gold answer, not a document list. The metric decomposes that gold answer into claims or sentences, then asks — usually via an LLM judge — whether each claim is attributable to the retrieved context:

Context recall=gold-answer claims supported by retrieved contexttotal gold-answer claims \text{Context recall} = \frac{\text{gold-answer claims supported by retrieved context}}{\text{total gold-answer claims}} Context recall=total gold-answer claimsgold-answer claims supported by retrieved context​

The unit of accounting is the claim. Non-deterministic, costs LLM calls, and sensitive to how the judge parses the answer.

Where they disagree

  • Recall@k high, context recall low. The right documents were retrieved, but chunking split the answer so a needed fact landed outside the chunk boundary. The doc ID matched; the text did not carry the claim. Signal to fix chunk size or overlap.
  • Recall@k low, context recall high. A chunk the annotator marked relevant was missed, but the same fact appeared redundantly in a chunk that was retrieved. Recall@k penalizes a failure the user would never notice.

The second case is why recall@k is unforgiving on corpora with duplicated content — regulatory filings, incident reports restating the same indicators, or multilingual near-duplicates.

Use recall@k when tuning the retriever itself — sweeping k, comparing BM25 weight against dense weight, testing a reranker. You want a stable, fast, non-noisy number runnable hundreds of times without cost.

Use context recall when validating that the pipeline as a whole can answer the question, especially after changing chunking or embedding strategy. It catches the failure recall@k is blind to: right document retrieved, wrong span of it.

Practical note on labelling

Recall@k's labelling burden is often overstated. Bootstrap relevance judgments from gold answers: retrieve a deep top-50 with a permissive hybrid config, have a judge mark which chunks contain gold-answer claims, then freeze that set as labels. After that the metric runs deterministically and free, forever. The one-time LLM cost buys a reusable non-noisy benchmark — exactly what is needed when comparing retrieval configurations across many runs.

6. Precision@k vs Context Precision

The split mirrors the recall case with one extra wrinkle: precision@k ignores ranking order entirely, while context precision is fundamentally about where in the top-k the useful chunks landed.

Precision@k — purity of the set

Precision@k=∣relevant chunks in top-k∣k \text{Precision@k} = \frac{|\text{relevant chunks in top-}k|}{k} Precision@k=k∣relevant chunks in top-k∣​

The unit is the document ID and the denominator is just k. Retrieve 10 chunks, 4 labelled relevant, precision@10 is 0.4 — identical whether the 4 relevant chunks rank 1–4 or 7–10. Deterministic, no LLM, no cost.

Context precision — rank-weighted usefulness

RAGAS-style, and a ranking metric wearing a precision name. It walks the retrieved list position by position, judges whether each chunk is useful, then averages precision@i over positions where a useful chunk appeared:

Context precision=∑i=1kP@i⋅vi∑i=1kvi \text{Context precision} = \frac{\sum_{i=1}^{k} P@i \cdot v_i}{\sum_{i=1}^{k} v_i} Context precision=∑i=1k​vi​∑i=1k​P@i⋅vi​​

where viv_ivi​ is 1 if the chunk at position iii is useful. Because of the P@iP@iP@i weighting, a useful chunk at rank 1 contributes far more than the same chunk at rank 10. Relevance is judged by an LLM against the question (or gold answer), not looked up from labels.

Concrete divergence

Two retriever configs, both returning 10 chunks with 3 useful ones:

  • Config A ranks the useful chunks at positions 1, 2, 3 → precision@10 = 0.30, context precision ≈ 1.0.
  • Config B ranks them at positions 8, 9, 10 → precision@10 = 0.30, context precision ≈ 0.27.

Precision@k calls these identical. Context precision correctly says A is dramatically better — the generator attends more reliably to early context, and a smaller k would still work for A but return nothing for B.

Use precision@k when the concern is noise in the window — how much of what goes into the prompt is junk. It tells you k is set too high, or that hybrid fusion is dragging in loosely-lexical matches. It is also the right metric for cost work, since irrelevant chunks are tokens you pay for.

Use context precision when evaluating a reranker. Adding a cross-encoder rerank stage barely moves precision@k if the same 10 chunks return in a different order — the set is unchanged, so the ratio is unchanged. Context precision is one of the few metrics that registers the improvement. In that role it overlaps heavily with MRR and nDCG; if graded relevance labels already exist, nDCG is the stronger choice — same order-sensitivity, deterministic, free to recompute.

Note on naming

RAGAS-family names are a persistent source of confusion: "context precision" measures ranking rather than purity, and its non-order-sensitive sibling is sometimes exposed separately as context relevance or context utilization. When wiring these into a comparison harness, read the framework's implementation rather than trusting the name — the same label denotes meaningfully different formulas across RAGAS versions, DeepEval, and TruLens.

7. Chunk Attribution vs Citation Coverage

Different questions. Chunk attribution asks where the answer came from (retrieval versus parametric memory); citation coverage asks whether the answer tells the reader where it came from. One is provenance measurement, the other disclosure measurement.

Chunk attribution — provenance

Measures what share of the generated answer traces back to retrieved chunks. The failure it catches is the generator answering from pretraining knowledge while retrieval sits unused in the prompt.

That failure is easy to miss because the answer can be entirely correct. Ask about a well-documented 2016-era influence campaign and the model may produce a solid answer from parametric memory, ignoring the corpus completely. Chunk attribution reveals that the retrieval pipeline contributed nothing — which matters enormously when the point of the system is that answers rest on a curated evidence base rather than on whatever the model absorbed in training.

A related diagnostic is chunk utilization: of the chunks retrieved, how many were actually used. Attribution looks from the answer backward; utilization looks from the retrieved set forward.

Citation coverage — disclosure

Measures what share of claims carry an attached source marker. The failure is an answer that is grounded but silent about it — the reader cannot verify.

Two strictness levels, and conflating them causes trouble:

  • Weak form — every claim has a citation marker, and the marker resolves to a chunk that was genuinely retrieved. Pure string and ID checking, fully deterministic.
  • Strong form — the cited chunk actually supports the claim attached to it. Needs a judge, and this is where most systems quietly fail, because models are good at attaching a plausible-looking citation to the wrong chunk.

The four-quadrant view

The two are independent, which is the clearest argument for tracking both.

  • High attribution, high coverage — target state. Grounded and transparent.
  • High attribution, low coverage — grounded but unciteable. Common with generic prompts that do not request markers. Fixable in the prompt, not the retriever.
  • Low attribution, high coverage — the dangerous quadrant. The model answered from memory then decorated it with citations that look right. Weak-form coverage passes; strong-form coverage catches it.
  • Low attribution, low coverage — retrieval is being ignored outright. Check whether context is even reaching the model.

That third quadrant is the reason to run both rather than treating coverage as a proxy for grounding.

8. Operational and System Metrics

Quality metrics alone are insufficient — evaluate the pipeline as users experience it.

  • Latency at p95 and p99 rather than median, since median hides the worst experience.
  • Cost per query, essential when trading off retrieval depth.
  • Task success measured offline against labelled traces.
  • Safety and compliance checks such as refusal rates and policy violations.

For DISARM/FIMI-style corpora, citation coverage is worth adding as a first-class metric alongside faithfulness, and stress tests benefit from custom evaluators like brand-safety or refusal checks rather than generic scores.

9. Using Judge Metrics in CI

The practical consequence of determinism is which metrics can gate a build. Deterministic metrics give a fixed number for a fixed input, so a regression threshold means something. LLM-judge metrics have run-to-run variance even at temperature zero, so a 0.02 drop may be noise rather than a real regression.

Three habits make judge metrics usable as gates anyway:

  • Pin the judge model and version, and treat a judge upgrade as a benchmark reset rather than a comparable run.
  • Average over 3–5 repeats per item and track variance, so the noise floor is known before setting a threshold.
  • Calibrate the judge once against human labels on a sample, so its agreement rate is known rather than assumed.

Applying this to config comparisons

For sweeping hybrid BM25-plus-dense weights, run the deterministic block only — recall@k, precision@k, nDCG, latency, cost. This gives free, noise-free, hundreds-of-runs-per-hour iteration, and nDCG covers the ranking sensitivity one would otherwise reach for context precision to get.

Bring in the LLM-judge block once the retriever is frozen, to answer the questions labels cannot: whether chunk boundaries actually carry the claims, and whether the generator stays grounded in what it was handed.

10. Staging Your Evaluation

Match the metric to the phase of work rather than tracking everything continuously.

  1. While tuning chunking and retrieval, focus on chunk-level relevance and ranking quality; once stable, tracking them can stop.
  2. Run regression gates in CI across ingestion, chunking, retrieval, reranking, and generation as a pipeline, not as isolated components.
  3. In production, track a few high-signal metrics — faithfulness, format correctness, answer completeness — plus analytical checks like topic coverage.

Tooling

The four-metric core (faithfulness, answer relevance, context precision, context recall) is implemented across RAGAS, DeepEval, TruLens, and ARES on the open-source side, and LangSmith, Arize Phoenix, and Braintrust commercially. Evidently ships built-in precision@k and hit-rate alongside customizable LLM judges.

A caution on reference-free judges

When gold answers are unavailable, proxy signals like response structure, tone, length, or completeness are still usable — but they correlate loosely with correctness. For retrieval precision work at any depth, invest in a labelled gold set. It unlocks recall@k, nDCG, and answer correctness, which are the metrics that actually discriminate between two competing hybrid BM25-plus-vector configurations.

11. Domain Notes for DISARM and FIMI Work

For structured threat-intelligence output, priorities differ from a general chatbot's.

  • Chunk attribution is the build-time metric. It shows whether the retrieval investment pays off at all. Check it specifically on queries about well-known campaigns, where parametric leakage is most likely and hardest to spot.
  • Strong-form citation coverage is the production requirement. A technique mapping or attribution claim citing the wrong report is worse than one citing nothing.
  • Split the CI and sampling load. Run weak-form coverage as a cheap deterministic gate on every build; sample strong-form coverage with a judge on a fixed evaluation set.
  • Note the overlap with groundedness. Strong-form coverage and per-sentence groundedness overlap substantially. The difference: groundedness checks a claim against the whole retrieved context, while strong-form coverage checks it against the specific chunk the answer pointed to. The latter is stricter, and it is the one that matters when a reader clicks a footnote.
