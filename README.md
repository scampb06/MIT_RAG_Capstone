# Capstone project for MIT RAG course

A retrieval-augmented question answering system over a corpus of 2,419 English Wikipedia articles, built checkpoint by checkpoint: from a no-retrieval baseline, through hybrid retrieval and an evaluation harness, to chunked, decomposed and graph-based advanced retrieval, and finally an agent-based system that plans its own retrieval.

## Installation

Tested on Windows 11 with Python 3.12.

1. **Create and activate a virtual environment**, then install the dependencies:

   ```powershell
   python -m venv .venv
   .venv\Scripts\Activate.ps1
   python -m pip install -r requirements.txt
   ```

   [`requirements.txt`](requirements.txt) lists the direct dependencies, pinned to the tested
   versions. [`requirements-lock.txt`](requirements-lock.txt) is the exact environment the
   results were produced with, including every transitive package
   (`python -m pip install -r requirements-lock.txt`). It also contains packages used by the
   course modules outside this folder.

2. **Add an OpenRouter API key.** All model and embedding calls go through
   [OpenRouter](https://openrouter.ai/keys). Create a `.env` file in this folder or any folder
   above it:

   ```text
   OPENROUTER_API_KEY=sk-or-v1-...
   ```

   `.env` is git-ignored. Never commit it.

3. **The corpus is included; the indexes are not.** The 2,419 Wikipedia articles are in
   `Checkpoint 1.1/Wikipedia/`. The chunk caches and Chroma vector indexes under
   `Checkpoint 2.1/` are git-ignored, and are built automatically the first time a script
   needs them:
   - Parsing the corpus into chunks takes about 35 minutes.
   - Embedding the chunks with `openai/text-embedding-3-small` costs roughly $1–2 per index
     (estimate).
   - The table-rendered index used by the 5.1 v2 agent can be built ahead of time with
     `python "Checkpoint 5.1/capstone_checkpoint_5_1_agent_rag_solution.py" --build-tables-index`.

4. **Checkpoint 6.1 security tools (optional).** Install these outside the project
   environment, so their dependencies cannot change the packages the agent needs:
   - [promptfoo](https://www.promptfoo.dev/) (Node.js) for the red-team and prompt-injection
     tests in `Checkpoint 6.1/redteam/`.
   - `semgrep` and `pip-audit`, each in its own virtual environment, for example:

     ```powershell
     python -m venv $HOME\.venvs\pip-audit
     & $HOME\.venvs\pip-audit\Scripts\python.exe -m pip install pip-audit
     & $HOME\.venvs\pip-audit\Scripts\pip-audit.exe -r requirements-lock.txt --no-deps --disable-pip
     ```

   Installing `semgrep` into the project environment downgrades the OpenTelemetry packages
   that `chromadb` depends on, and `import chromadb` then fails.

## Checkpoints

| Checkpoint | Summary |
|---|---|
| **1.1** | **Script** — [`capstone_checkpoint_1_1_baseline_solution.py`](Checkpoint%201.1/capstone_checkpoint_1_1_baseline_solution.py) establishes the no-retrieval baseline. It builds a plain LangChain chain over `openai/gpt-5.4-mini` via OpenRouter with no retrieval and no document parsing, runs the starter's example prompts plus six hand-written Wikipedia probes covering obscure facts, a direct quotation, a nonsense entity, a two-ceremony comparison and a post-cutoff event, and logs every prompt and response to `checkpoint_1_1_responses.log` so answers can be checked by hand against the real articles. |
| | **Findings** — The model fabricates confidently whenever a question outruns its parametric memory. It invented a Wikipedia article for the non-existent "huba juice", produced a period-styled but fictitious quotation from Charlotte Brontë's 1846 letter and named the wrong publisher, gave Calton's 2008 male life expectancy as 53 rather than 54, named the wrong Best Supporting Actor presenters at both the 85th and 95th Academy Awards, and combined stale Apollo and Artemis facts into a false claim that a 2026 Moon landing was expected. Behaviour was inconsistent, with the same nonsense question sometimes drawing an honest refusal. Conclusion: retrieval is required to ground answers, but it will not stop hallucination on out-of-corpus or nonsensical questions unless the prompt confines the model to retrieved text. |
| **2.1** | **Script** — [`capstone_checkpoint_2_1_baseline_retrieval_solution.py`](Checkpoint%202.1/capstone_checkpoint_2_1_baseline_retrieval_solution.py) implements the baseline hybrid retriever. `extract_wikipedia_text()` pulls plain text from each HTML article with trafilatura, `build_or_load_wikipedia_db()` embeds whole articles into a persistent Chroma store, and `WikipediaHybridRetriever` fuses BM25 keyword scores with vector similarity at equal weight after min-max normalisation, drawing from a candidate pool of 10 and passing the top 3 whole articles to the LLM. It then runs 15 test queries spanning representative and two rounds of adversarial cases, logging retrieval and answers to `checkpoint_2_1_retrieval.log`. |
| | **Findings** — Hybrid retrieval handled single-article lookups well, correctly finding that the 2011 Tōhoku earthquake shortened the day by 1.8 microseconds even when the query wording differed from the article. It failed on multi-entity and multi-article questions: the 85th/95th Academy Awards comparison retrieved three award-category pages instead of the two ceremony articles and wrongly attributed *12 Years a Slave* to the 85th, and both Olympics questions retrieved thematically adjacent but wrong-year articles. Diagnosis: `TOP_K=3` over whole articles lets adjacent documents crowd out required ones, trafilatura flattens tables so their structure is lost, and on the Reagan/NFL query the model silently answered from parametric memory in violation of the system prompt. Proposed next steps were a higher top-k and candidate pool, title matching, splitting and chunking, richer extraction of headings, tables, wikilinks and infoboxes, and query decomposition. |
| | **Documentation** — [Program documentation for the extraction module](docs/Extract_text_and_links_from_wikis.md): per-article pipeline (Mermaid), node/edge/chunk data model, function reference for `Extract_text_and_links_from_wikis.py`. |
| **3.1** | **Script** — [`capstone_checkpoint_3_1_evaluation_solution.py`](Checkpoint%203.1/capstone_checkpoint_3_1_evaluation_solution.py) is the evaluation harness. It keeps the 2.1 hybrid retriever and adds a golden-suite loader, three LLM judges (correctness with graded levels, aspect coverage and relevance; claim-level groundedness, citation support and chunk attribution measured against a closed-book answer; and refusal behaviour) plus deterministic retrieval, citation and quote metrics — 19 in total across retrieval, generation and operations. Results are written per record to JSON and CSV in `evaluation_results/`, with a summary printer, an `--input` flag to select a suite, and a `validate_framework()` check that the judge passes a correct answer and fails a manipulated one. |
| | **Findings** — The baseline scored 12/18 (66.7%) correct on the generated suite and 9/15 (60%) on the handcrafted one, with mean precision of 53.7% and 31.1% respectively; four handcrafted records retrieved none of their required documents. Retrieval is the principal bottleneck — whole-article search at `TOP_K=3` gives a poor signal-to-noise ratio — but generation problems were more common than expected, including misattributed citations, unsupported claims and one answer drawn from parametric memory. The framework itself proved reliable and reproducible, catching a citation misattribution in Q011 and an unsupported editorial claim in Q094 across two independent runs, but it has blind spots: honest refusals are penalised as ungrounded because no document asserts an absence, and complete, well-cited answers were sometimes falsely flagged as hallucinated. Cost of about 15 cents per query exceeded the 10 cent budget, and latency needed percentile rather than mean reporting. Notably, the handcrafted queries exposed more weaknesses than the automatically generated suite. |
| **4.1** | **Script** — [`capstone_checkpoint_4_1_advanced_retrieval_solution.py`](Checkpoint%204.1/capstone_checkpoint_4_1_advanced_retrieval_solution.py) adds advanced retrieval to the 3.1 harness with the judges and metrics carried over unchanged, so every configuration is scored by the same instruments. A `--retriever` switch selects four strategies behind a single seam: baseline whole-article fusion; chunks, retrieving over 134,107 chunks at top-k 8 from a candidate pool of 40; decompose, which splits a query into LLM sub-queries and sums fused scores per chunk; and graph, a NetworkX layer of 28,054 nodes and 56,761 edges that expands seed articles through category, infobox and hyperlink relations with primary versus context labelling. It also adds `--parent` expansion with a context budget, a resumable `--build-index`, a cost-free `--retrieval-only` mode, rate pacing with retries, incremental result saves, and chunk-aware metrics including evidence recall and matched-count recall over the first three articles. |
| | **Findings** — All three advanced retrievers improved retrieval sharply — strict recall rose from 6% to 41%, 47% and 59% and evidence recall from 36% to about 50% — while context per query fell from 225k to 25–39k characters and cost from $3.00 to between $0.40 and $0.60 per 17 records. Correctness moved far less: 6/17 for chunks, 7/17 for decompose and 8/17 for graph against a baseline of 7/17, though graded correctness rose from 0.47 to 0.66 under the graph retriever. Each technique won where predicted and lost elsewhere: chunking fixed long-document dilution but its capped parent policy lost Q049; decomposition solved multi-entity comparisons such as Q003 but halved chunk attribution from 0.62 to 0.48 by naming answer entities in sub-queries from the model's own knowledge; and the graph alone solved the unnamed-entity records G08 and G13 while dropping precision to 26% through over-broad expansion. The remaining failures are mostly generation-side, and the proposed next step is an orchestrator that routes each query to the retriever best suited to it. |
| | **Documentation** — [Program documentation for the advanced retrieval script](docs/capstone_checkpoint_4_1_advanced_retrieval_solution.md): program flow (Mermaid), class and function reference, CLI, data artifacts. |
| **5.1** | **Script** — [`capstone_checkpoint_5_1_agent_rag_solution.py`](Checkpoint%205.1/capstone_checkpoint_5_1_agent_rag_solution.py) turns the 4.1 retrievers into tools for a LangGraph agent that plans its own retrieval. It runs three versions behind `--agent-version`: v0, the fixed 3.1/4.1 whole-article pipeline as the baseline; v1, the initial agent; and v2, the refined agent. Each query runs a free seed chunk search, then a planner loop that assesses the evidence, picks one action (`chunks` with a parent width, `decompose`, `graph`, `clarify` or `answer`, plus `title_search` and `read_section` in v2), and fuses the results by reciprocal rank into a 40k-character context, for up to three planned steps. v2 adds a question-only clue step and a code-level check that every clue is backed by a quote-verified fact before an answer is allowed, and it can read a table-rendered index built with the 2.1 module's new `render_wikitables()`. Each round-2 refinement can be switched off with `--disable`, and `--planner-model`, `--answer-model` and `--reasoning-effort` select models per role. The 4.1 script is imported unchanged, so every 4.1 judge and metric scores the agent; `--judge-repeats` adds majority voting. It runs in batch, single-question (`--question`) and interactive (`--chat`) modes. |
| | **Findings** — v0 reproduced the 4.1 baseline exactly, with identical retrieval on all 17 records ([sanity report](Checkpoint%205.1/evaluation_results/v0_vs_4_1_baseline_sanity_report.md)). The initial agent beat it at a fraction of the cost: correctness rose from 7 to 11.5 of 17 by majority vote, strict source recall from 6% to 65%, and cost fell from $2.99 to $0.43 per run, because the agent reads about 18k characters of targeted passages instead of about 225k of whole articles. Weaknesses remained: it filled in bridge facts from memory (Q009), could not read further into an article it had found (Q049, G13), and misread complex tables (Q014) ([initial evaluation](Checkpoint%205.1/evaluation_results/v0_vs_v1_initial_evaluation_report.md)). The v2 refinements fixed specific failures: `read_section` reached the label-less winners-table chunk on Q049, and the clue step made Q009 the first bridge answer grounded in retrieved evidence. On gpt-5.4-mini, though, correctness stayed at 11.5 of 17, because the remaining failures were judgement failures of the planner and answer model. Changing models moved the results most: Claude Haiku 4.5 as planner and answer model reached 13.5 of 17 and graded correctness 0.88 at $0.82 per run, and Q014 needed both the table rendering and the stronger answer model. Medium reasoning added cleaner citations at double the latency, and facet choice for category intersections (G10) is still unsolved. Single correctness verdicts proved too noisy to compare versions, so all comparisons use majority votes over repeated runs ([refinement report](Checkpoint%205.1/evaluation_results/v1_vs_v2_refinement_report.md)). |
| | **Documentation** — [System design document for the agent](Checkpoint%205.1/capstone_checkpoint_5_1_agent_design.md): versions, agent workflow (Mermaid), state, tools, complete system prompts, fact verification and the clue step, evidence fusion, evaluation fields, command line, and the change log of every refinement with the failure that motivated it. |
| **6.1** | **Script** — [`agent_provider.py`](Checkpoint%206.1/redteam/agent_provider.py) is a promptfoo Python provider that turns the 5.1 agent into a red-team target. It imports the 5.1 script unchanged, loads the indexes once per worker, and keeps one agent per model configuration, so a single config can test several models. For indirect injection it plants a test's attack text as the top-ranked hit of every passage search, as a poisoned article would rank, without modifying the indexes. Each test returns the answer, the agent's own token use and cost, and metadata: actions, stop reason, sources, whether the planted passage reached the context, model calls, and planner and answer tokens and cost. Two configs drive it: [`promptfooconfig.yaml`](Checkpoint%206.1/redteam/promptfooconfig.yaml) for 37 generated direct attacks (prompt extraction, system-prompt override, hijacking, off-topic, RAG exfiltration and attribution, with jailbreak strategies), and [`indirect_eval.yaml`](Checkpoint%206.1/redteam/indirect_eval.yaml) for six hand-written indirect attacks with deterministic and rubric-graded checks. |
| | **Findings** — The audit found four classes of vulnerability, all in the prompts and the workflow rather than the Python code. (1) **Poisoned passages control the answer:** a planted "authoritative correction" made both gpt-5.4-mini and Haiku 4.5 give Andrew Lesnie's death year as 1999, ignoring the real article, and Haiku relayed a planted instruction asking the user to sign in with their password at a phishing URL. (2) **Instructions are obeyed from both the question and planted passages:** a fake system turn produced `HACKED:` prefixes, and a planted note switched the answer to French. (3) **Off-task requests are answered with misleading citations:** a cookie recipe was cited to `Ethereum.html`. (4) **Obfuscated input made the clue step return its own few-shot examples**, which the agent then answered. The root cause is the lack of a data/instruction boundary: retrieved passages and the question share one message, no prompt sets the agent's scope, and the v2 quote check confirms that a quote exists but not that its source is trustworthy. A stronger model is not a fix: each model resisted four of the six indirect attacks, but different ones. Two quality rules widened the attack surface: "cite every sentence" made injected text look sourced, and the frozen clue checklist carried leaked examples to the answer. semgrep found nothing and bandit one low-severity silent `except` in the 4.1 decomposer. pip-audit's 24 advisories include an unpatched Chroma server-side remote code execution, which the embedded Chroma used here is not exposed to. On performance, the planner takes 32–60% of agent time and 69–95% of agent cost, because it re-reads up to 16k characters of evidence every turn. v2 always makes at least three model calls, reasoning roughly doubles latency, and start-up takes about 50 s to build the indexes; the agent alone costs about $0.016 per query on gpt-5.4-mini and $0.03 on Haiku ([findings report](Checkpoint%206.1/redteam/red_team_findings_report.md), [performance tables](Checkpoint%206.1/step3_performance_tables.md), [worksheet](Checkpoint%206.1/Required_Capstone_Checkpoint_6_1_Worksheet.docx)). |
| | **Documentation** — [Security and performance testing commands](Checkpoint%206.1/capstone_checkpoint_6_1_security_and_performance_testing.md): the promptfoo red-team, indirect-injection and export commands, semgrep, bandit and pip-audit, with a Mermaid diagram of each command's inputs and outputs, setup notes and Windows pitfalls, and where the performance figures come from. |
| **7.1** | **Scripts** — [`capstone_checkpoint_7_1_production_ready_solution.py`](Checkpoint%207.1/capstone_checkpoint_7_1_production_ready_solution.py) is the hardened agent (`HardenedAgent`), which subclasses the 5.1 v2 agent and imports it unchanged. It adds six security layers, each switchable with `--disable`. (1) `structure`: every model call gets XML-tagged inputs (`<user_question>`, `<evidence>`, `<documents>`, `<passage>`) under a trust hierarchy in which both user text and retrieved passages rank below the system prompt, and the agent's reserved tag names are escaped wherever they appear in inserted text. (2) `contract`: answers are always English prose, actions such as sign-ins are never relayed, a planted "correction" loses to a conflicting article, and claims are cited only where a document states them. (3) `sanitize`: regular expressions strip fake role messages, known jailbreak templates, pasted sources and base64/hex payloads, and refuse input with no answerable question, all before any model call. (4) `filter`: gpt-5.4-nano removes persona and instruction-override spans, verified word for word, and fails open on an outage. (5) `scope`: scope rules and a new planner `refuse` action decline off-task requests while still answering the legitimate part. (6) `clue_guard`: the clue step can no longer echo its own examples. [`capstone_checkpoint_7_1_tuned.py`](Checkpoint%207.1/capstone_checkpoint_7_1_tuned.py) layers five switchable performance features on the hardened agent, which it imports unchanged. `sparse_bm25` gives exact BM25Okapi scores from a precomputed SciPy sparse matrix saved next to the chunk cache. `repair` fixes near-miss planner quotes (≥ 90% similar) instead of calling the planner again. `fast_path` is a deterministic rule that sends single-article questions straight from the seed search to the answer step, with a code check and fallback to the full agent. `selective_reasoning` reasons only on multi-hop, comparison and yes/no questions and later planner turns. `cache` is opt-in (`--cache PATH`): [`semantic_cache.py`](Checkpoint%207.1/semantic_cache.py), a semantic answer cache with LFU-with-aging eviction, a calibrated 0.934 similarity threshold, number, pronoun and follow-up guards, and atomic JSON persistence, consulted only after the input guard. [`cache_harness.py`](Checkpoint%207.1/cache_harness.py) simulates eviction policies, calibrates the threshold and runs a live cache workload, and [`tuning_report.py`](Checkpoint%207.1/tuning_report.py) builds the before/after tables from saved runs. The 6.1 promptfoo provider gained `7.1` and `7.1-tuned` targets, with a 37-probe replay ([`redteam_replay.yaml`](Checkpoint%206.1/redteam/redteam_replay.yaml)) and eight attack-like benign questions ([`benign_eval.yaml`](Checkpoint%206.1/redteam/benign_eval.yaml)). A new 24-question one-hop suite ([`simple_one_hop_suite.json`](Checkpoint%207.1/simple_one_hop_suite.json), drawn from the 3.1 tests) complements the 17-question golden suite. Offline self-checks (`--self-check`) cover every layer and feature without API calls. |
| | **Findings** — **Hardening** closed all four 6.1 vulnerability classes. Indirect injection rose from 4/6 to 6/6 attacks resisted on both gpt-5.4-mini and Haiku 4.5 (the Lesnie "1999" correction, the French switch and the phishing relay all fixed). In a replay of the 37 red-team probes, answers that obeyed the attack fell from 11 to 0. 34 probes were defeated before the answer step: 16 stopped by the input guard, 14 refused by the planner, and 4 whose attack text the sanitizer removed before the legitimate question was answered. The answer prompt resisted the remaining 3. All 8 benign questions that look like attacks were still answered, and golden-suite correctness was unchanged at 11.5 of 17. The cost on legitimate questions was about 3 s (about 30%) more latency at p50 and 19% more agent cost; attack probes became 60% faster and 67% cheaper because refusals end the run early ([evidence summary](Checkpoint%207.1/step4_evidence_summary.md)). **Tuning** offset most of that. Offline profiling first found that `rank_bm25` took 853 ms per search and 21 s to build at every start, and that v2 answered 38% of 6.1 queries straight after the seed search while still paying for a clue call and a planner call ([Phase 0 findings](Checkpoint%207.1/evaluation_results/phase0_tuning_findings.md)). Sparse BM25 cut a search to 1.9 ms with identical rankings, and BM25 start-up to about 1 s. With the fast path, mean agent latency fell 12% on the golden suite (17.9 → 15.7 s) and 21% on the one-hop suite (17.6 → 13.9 s), and agent cost per query fell 4% and 14%. Retrieval p50 dropped from about 2.9 s to under 0.9 s, planner calls fell 12–18%, and correctness held (11.5 → 11.0 and 17.0 → 18.5, within run-to-run noise). The fast path answered 25% of one-hop and 12% of multi-hop questions; on those, 11 of 16 answers passed against 9 of 16 for the hardened agent. Security results were unchanged on the tuned agent (6/6, 0/37, 8/8). With Haiku, selective reasoning beat reasoning on every call (42.9 → 37.2 s, 14.0 → 15.0 correct), but no reasoning at all was as correct at half the latency. Threshold calibration showed that the planned 0.90 cut-off would have served "In what year was Andrew Lesnie born?" the stored death year (similarity 0.928), so the threshold was raised to 0.934. In a live workload the cache then served 10 of 12 repeats and paraphrases with 0 wrong answers, in 3.0 s and $0.00007 per hit against 8.5 s and $0.0039 for a full run. LFU with aging also beat Lab 7.2's FIFO eviction in simulation (29–56% against 15–46% hit rate). Remaining limits: a 3.1 s minimum gap between model calls, inherited from 4.1's rate-limit pacing, is now about half of the tuned agent's time in evaluation runs. Some failures come from over-strict rubrics (G10, Q021, Q054, Q095). Others are passages never reached inside long articles (Q082) and tables misread across neighbouring records (Q084). The proposed `expand` action, a `find_categories` tool, table captions carried into rows, and a server process that would give the cache shared use are all future work ([tuning results](Checkpoint%207.1/evaluation_results/tuning_before_after.md), [cache evidence](Checkpoint%207.1/evaluation_results/cache_report.md), [worksheet](Checkpoint%207.1/Required_Capstone_Checkpoint_7_1_Worksheet.docx)). |
